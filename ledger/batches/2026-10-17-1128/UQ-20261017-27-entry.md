Domain(s): AI architecture — distributed training systems (secondary: scaling methodology). Method transplanted from industrial metrology (variance components / gauge R&R).
Question (canonical): For one pretraining recipe at a scale where several parallelism configurations are feasible, run a crossed design of C ≥ 3 configurations × S ≥ 3 seeds — holding global batch size, global-batch membership and order, seed, numeric formats and token count fixed, and restricting C in advance to a matchable set of changes that provably do not alter the mathematical objective (excluding e.g. Megatron-LM #7464 vocab-parallel label smoothing on the local vocabulary, #1754 non-divisible vocab) — what are the between-configuration and between-seed variance components with confidence intervals, what interval covers σ²_config/σ²_seed for (a) held-out loss at fixed token count and (b) each member of a pre-registered downstream metric set, is the upper confidence limit of that ratio below 1 (the invariance verdict), and which axis (rank count, micro-batch count, sharding style) carries any excess?
Alternative formulations: (1) Is "same recipe, different GPU layout" the same experiment, and by how much is it not? (2) How much of the difference between two training runs is attributable to how the run was sharded rather than to the recipe? (3) The elastic-training literature ships a binary "accuracy consistency" predicate — what is the magnitude behind it, and where does it sit relative to seed noise?

Significance — consequence: Invariant ⇒ the field's eyeballed regression-test practice is calibrated for the first time: framework teams get a published tolerance for "loss curves match" gates, cross-configuration comparisons become defensible, FlexTrain's "relaxed consistency" tier can be declared free. Not invariant ⇒ every comparison whose arms differ in layout carries a treatment-correlated nuisance factor, biting hardest where layout moves with the treatment (scaling ladders; recipe ablations run at one sharding and shipped as general advice), and release notes asserting "no convergence impact" become unquantified claims. The axis decomposition says what to fix: micro-batch count → fixed accumulation tree; rank count → deterministic collectives; sharding style → the invariance claim must be weakened in the frameworks' own docs.
