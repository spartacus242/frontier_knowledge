## Restatement (my own words, before attacking)

Model families keep announcing bigger context windows in big jumps. For open-weight families that have shipped at least two such jumps, take each jump from the old advertised limit L_prev to the new one L_new and ask four things. (a) On a specific, named, dated, public corpus of real request lengths, split by workload type (chat / coding agent / document QA / long tool-trace agent), what fraction of requests are longer than the OLD limit — i.e. how often was the old window actually the binding constraint? (b) Taking only those over-the-old-limit requests, does serving them at the new limit produce a better task result than cutting or compressing them down to the old limit (with retrieval-plus-truncation as the fair baseline)? (c) What does a request cost to serve with the window set at L_new versus L_prev? (d) Did the family's short-context quality move between its pre-extension and post-extension checkpoints on one fixed eval harness? The implied verdict question: was the last window increase worth what it cost, measured against real traffic rather than synthetic needle benchmarks?

Two things I note about the carried-forward wording before testing it. First, limb (b) is an *interventional* comparison **on the exceeding stratum of C** — it needs the actual requests, re-run twice. Second, the reformulation requires C to be "NAMED, DATED, PUBLIC" and the record **names no C anywhere**; C is a free variable the record treats as pinned.

## Attack 4 — conditioning clauses, written out first, then tested

Numbered literally from the Gate 1 canonical wording. MEASURAND EXEMPTION DECLARED, not merely considered: the exceedance share s itself (limb a), the sign of the short-context delta (limb d), and the absence of a published marginal-value figure (P6) are all *reported quantities* in this question, so attack 4 does not reach them and I did not grade around them. What follows is the set of clauses that must be true *before the question can be asked at all*.

- **C1. At least two open-weight families each have >=2 announced context-length increases.** TRUE for one step of one family, sourced: the Llama-3.1-8B-Instruct card states 128k and prints a Llama 3 8B comparison column. UNVERIFIED for "two families" — I opened no Qwen/Mistral/DeepSeek/Gemma card. Kills nothing.
- **C2. For each step the family supplies pre- and post-extension checkpoints whose short-context delta attributes to the extension.** CONTESTED (sourced). The Llama 3.1 card never describes 3.1 as an extension of 3: it reports a ~15T-token pretrain with a December 2023 cutoff and lists the longer window among "new capabilities" of a new release. Literally the question only needs two checkpoints labelled pre/post by release order, so C2 survives as worded — but then limb (d) measures a release-to-release delta, not the extension's cost, which is what the intake wording ("costs incurred to support it") asks for.
- **C3. A single named, dated, public request-length corpus C exists that is stratifiable into chat / coding agent / document QA / long tool-trace agent.** FALSE on every corpus I opened (5 of 5), and the record names no C: Azure 2024 splits only code vs conversation; BurstGPT only "Conversation log" vs "API log"; ServeGen is a generator, not a corpus; cc-traces-weka is agentic coding only; WildChat-1M is chatbot conversations only. Each supplies at most two of the four classes.
- **C4. C's exceeding stratum can carry a task-outcome experiment — serving at L_new versus truncating/compressing to L_prev.** This needs prompt CONTENT, because the comparison is interventional: you must re-run the request twice. FALSE on all four length corpora I opened — Azure, BurstGPT and cc-traces log token counts and no text, and cc-traces' lengths are not even token counts ("always an exact multiple of 64, not a true tokenizer count"). Azure prints the structural reason verbatim: "Due to customer privacy requirements (e.g., GDPR), we do not have visibility into the content of the prompts", and documents the substitute everyone uses — "we send the input prompt with the required number of tokens" — which is a *length-matched synthetic* prompt and carries no task outcome. The one content-bearing corpus I opened, WildChat-1M, has text but no token counts and no agent or tool-call class. So on everything I opened, content and length-by-serving-class do not co-occur, and limb (b) collapses into limb (a): with lengths alone, "would have been truncated at L_prev" is just s restated, and cannot distinguish truncated-and-fine from truncated-and-failed, which is the whole content of the question's pre-declared negative. **CAVEAT, flagged not buried: my own D9 returned SWE-chat (arXiv:2604.20779), a reported 301,000-session Copilot agent-trace release, and TraceLab, and I opened NONE of them. If any supplies real production requests with full prompt text plus per-request token lengths, C4 flips to TRUE for one class.** I therefore do not rest the verdict on C4.
- **C5. Input lengths in C are generated independently of the window under which they were served, so P(input > L_prev) measured on C estimates the demand that L_prev would have failed.** **FALSE for the agent class, sourced on a paper I opened in full.** PRIOR 4 shows the client harness actively compacts *against the limit*: compaction fires in "7.8% of all agent sessions", "22.6% among long-context sessions" and "0.5%" of calls, and "the median event drops 72.8% of prompt tokens", with trigger points distributed below the limit (paraphrase). Request length in that class is therefore an *output* of a policy aimed at the current window, not an exogenous property of demand. Under L_prev the same harness would have compacted earlier and more often and produced shorter inputs; so s measured on traffic served at L_new is not the counterfactual share that L_prev would have failed, and the bias is not even signed — truncation policy pushes observed lengths down while a larger window invites longer histories, pushing them up. Nothing in the four limbs identifies that counterfactual, and nothing in P1-P6 mentions it: P1 is about representativeness and model-mixing, P2 about outcome measurability. This is the clause the question's own stated negative answer ("exceedance shares of a few percent ... would say the last doubling's realized value was negative") cannot survive without, because that inference reads s as demand.
- **C6. Serving cost per request differs between a deployment configured at L_new and one configured at L_prev.** UNVERIFIED. I opened no serving-engine document. I will not assert the paged-KV argument I am tempted to make, because I cannot source it in this budget, and an unsourced technical claim kills nothing here.
- **C7. The announced length is chosen at least partly on expected value (P4).** UNVERIFIED.

Multi-leg discipline: this kill has two legs, sourced separately. **The verdict stands on C5 alone** — one paper, opened at full-text level, in the workload class the record itself names as most likely to bind. C3/C4 are support, each sourced on five opened dataset cards, and C4 carries a named unopened repair that could flip it. If C3/C4 fell entirely, C5 still stands; if C5 fell, C3/C4 would leave attack 4 at Partial, not Unresolved.
