## Gate 0 — Intake

Question (canonical, version A as intaken): Across shipped LLM tokenizer configurations, what fraction of real-world documents fails the round trip decode(encode(d)) = d, how is that failure distributed across scripts and orthographic features (Unicode normalisation classes, combining marks, zero-width joiners, whitespace runs), and does the per-language round-trip failure rate confound published per-language loss and multilingual benchmark comparisons?

Question (canonical, version B — Gate 1 reformulation, one permitted, well-posedness only; this is the version graded): For a frame of T >= 6 tokenizer configurations drawn by a rule fixed before any data pull (the T most-downloaded open-weight multilingual base-model repositories on the Hugging Face hub carrying a distinct `tokenizer.json`/`tokenizer.model`), each pinned by repository revision hash, and one pinned, dated, script-stratified multilingual document sample: (a) what is the document-level and codepoint-level rate at which decode(encode(d)) != d, under both criterion 1 (exact string identity) and criterion 2 (identity up to the configuration's own declared normalisation), with CIs; (b) how does that rate decompose by script and by orthographic feature (normalisation class, combining mark, ZWJ, whitespace run), and what share of it is equivalence-preserving versus meaning-changing; (c) by mechanism (normalisation step, control-character stripping, absent byte fallback, decoder whitespace rule); and (d) when per-language held-out loss is recomputed on the round-trip-stable subset versus the full sample, what share of one named published cross-language loss gap does the difference account for?

Reformulation rationale (recorded per Gate 1): version A left two things unfixed that version B fixes — the sampling frame for "shipped tokenizer configurations" (no selection rule, so the tokenizer denominator floated), and "published per-language loss" (no named gap, so the confound limb's estimand had no referent). Nothing about the object was changed.

Alternative formulations:
1. Is tokenization actually lossless for the languages we evaluate — and if not, for which scripts is per-language perplexity being computed against a corrupted target?
2. How much text can a shipped tokenizer not represent at all, and does that unrepresentable share track the languages where models are reported to be weakest?

Motivating gap (as intaken, and its Gate 2 correction): The settled claim being inverted is that subword tokenization is a lossless, invertible encoding, which is what licenses reading per-language loss and multilingual scores as properties of the MODEL. Shipped tokenizer configs routinely include irreversible steps — Unicode normalisation, control-character stripping, whitespace collapsing, decoder rules — and byte fallback is a config option that is not always on. The intake premise that "the tokenizer literature measures fertility, compression and cross-lingual cost parity, not round-trip fidelity" is FALSE as of 2026-08 and this is the Gate 2 finding: TokEval (arXiv:2608.18062v3) carries a section headed "Encoding fidelity" (§3.4) that defines round-trip reconstruction x̂ = T⁻¹(T(x)), measures it with Reconstruction Exact Match ("the rate at which decode(encode(x)) equals x exactly") and CER, and names the same three mechanisms the candidate names. The intake's novelty check was declared unrun, so this is the first check that ran on this limb, and it goes against the candidate.

## Gate 3 — Significance

Significance — consequence: If round-trip failure is non-trivial and script-skewed, then published per-language loss and multilingual benchmark gaps are partly a property of the encoder, not the model, and a per-script table would change which tokenizer a multilingual pretraining team picks and force low-resource evaluations to report a fidelity figure alongside the score — the same move the field already made for contamination. If rates are near zero or wholly equivalence-preserving, the result positively licenses the current practice of reading per-language loss as a model property, which is worth having stated rather than assumed. Note the consequence is now carried by limbs (b) and (d): limb (a)'s consequence has been largely pre-empted by TokEval's metric, whatever its values turn out to be.

Significance — audience: Multilingual pretraining teams choosing a tokenizer, and maintainers of low-resource-language evaluations, would act on a per-script table. Real and identifiable: the tokenizer-fairness line of work exists, TokEval's own §3.3 reports a Tokenizer Fairness Gini, and arXiv:2608.25089 shows a group actively arguing about which crosslingual metric is valid. The audience for limb (a) alone is now smaller, because TokEval already hands them the metric to run themselves.

Significance — fecundity: Opens: whether meaning-changing loss (ZWJ, combining marks) concentrates in the scripts where models are reported weakest; whether a fidelity figure belongs in model cards next to vocabulary size; whether byte fallback should be mandatory rather than configurable; whether retraining on round-trip-stable text changes per-language loss ordering; and whether evaluation harnesses should refuse to score a language whose fidelity rate exceeds a threshold.

Significance — anchoring: Touches the crosslingual-comparability problem (arXiv:2608.25089), tokenizer fairness and parity, the byte-level-model case (UTF-8 validity work, arXiv:2606.14122, returned not opened), Unicode normalization stability as a standards property (UAX #15 review record), and this ledger's own UQ-20261016-12 on config drift, which supplies P3's pinning requirement.

Reason for silence: A disciplinary-boundary plus incentive mechanism, and it is partly expired, which is itself the finding. Round-trip correctness was owned by library maintainers as a unit-test property — a bug to fix, a pass/warn/fail check — rather than by researchers as a measurand to report; query 9 confirms that the field owning the method (property-based and metamorphic testing) returns test tooling and no measurement, and queries 6–7 show the neighbouring fields (Unicode standards, DH corpus repair) carry the concept and no tokenizer incidence rate.
