Domain(s): Medicine — clinical prediction models / clinical decision support; method from software engineering (differential / N-version testing of independent implementations of one specification). Owning literatures are mHealth safety, medical-app assessment and clinical pharmacology, not clinical epidemiology.
Question (canonical): For a pre-declared set of published clinical risk scores each carrying a published action threshold, do independently written implementations return the same value for the same patient, at what rate do they disagree enough to cross the threshold, and what share of those crossings is implementation error rather than under-specification in the source publication? (V1, the one permitted Gate 1 reformulation, adds a pre-run partition of the input space into spec-determined and spec-undetermined regions, a pre-declared input-sampling rule weighted to boundary/unit/missing cases, and a chance-corrected adjudication statistic; V0 retained in the record, which is circular in using "faithful implementation" on inputs the publication does not determine.)
Alternative formulations:
1. Is a published clinical risk score a well-defined function of its inputs, or only a sketch each implementer completes differently?
2. How often does which calculator you open, rather than which patient you have, decide which side of the threshold the patient lands on?
3. (Method-field wording) What does N-version differential testing of deployed score implementations against their published specification find, and how much divergence is specification under-determination rather than defect?
Motivating gap: Intake held that software engineering routinely asks whether independent implementations of one specification agree while medicine treats each score as a fixed function and only compares *different* models (Framingham vs QRISK vs PCE). Gate 2 overturned the gap: the question is asked and substantially answered in medicine's own journals and in the method-owning field, in registers the intake did not try ("calculator app accuracy", "systematic assessment", "partition violation", "online GFR calculator accuracy"). Neamtiu 2023 states the intake's gap in its own abstract and then closes it.
Presuppositions:
1. Divergence from the published description is a defect, not local design choice — established in practice; contested for localised EHR builds, and additionally version-indexed (CKD-EPI 2009 vs 2021; FRAX v3.8 vs v4), a confound the record never named. Adversary 1 Partial; adversary 2 holds V1's pre-declared publication per score defuses it.
2. >= 3 inspectable independent implementations exist per score — over-established: 47 CKD-EPI calculators, 90 Android apps over 12 scores, 46 insulin-dose apps, 23 opioid-conversion apps. Fails only for proprietary EHR builds, which V1 excludes from S.
3. Disagreements can be adjudicated into coding error vs under-specification — established and already done: P1 separates specification from implementation error sources; N1 adjudicates all 28 errors to cause. 4. Each score has an action threshold whose crossing changes an action — true by construction of S; the record's supporting citation overreaches (P1's "Meets or Exceeds Threshold" column is undefined in the paper) but the question does not depend on it.
5. What would count as an answer: measured pairwise and set-wise any-difference rate and threshold-crossing rate across >= 3 implementations per score on a pre-declared sample, reported separately over the two regions, plus the adjudicated error/under-specification split with an agreement statistic, plus a per-score under-specification audit. Near-zero crossings on a grid that genuinely includes the awkward regions answers it in the negative — and that branch is already partly in hand (P2: 98.6% output accuracy, Child-Pugh errors did not change class; N2: limits of agreement <1% between two FRAX implementations on 1,254 patients).
