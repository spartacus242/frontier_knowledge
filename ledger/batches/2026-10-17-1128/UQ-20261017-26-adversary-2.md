## Restatement in my own words

When a production LLM server flips its speculative-decoding switch on, does the distribution of
text it actually serves move — not "is the rejection-sampling rule distribution-preserving on
paper", but does the *served* distribution move — and if so, how big is the move once you subtract
the move you would get anyway from changing nothing but the mix of other requests sharing the
batch? The question wants that excess as a number with an interval, on a fixed prompt set, against
a permutation null, and wants it compared to two reference sizes: one quantization step measured on
the same instrument, and the smallest benchmark difference the field prints as a result. The
question concedes up front that the two arms cannot be fully matched, because the speculative
target pass scores k+1 rows where plain decode scores 1, and that shape difference *is* the
treatment. A null answers it as well as a positive.

## The decisive find: vLLM #54506 (asked, in a vocabulary the record never searched)

https://github.com/vllm-project/vllm/issues/54506 — "[RFC]: Batch invariance for speculative
decoding needs to cover the forward pass (M=1 vs M=k+1)", opened 2026-08-31, open, labelled
`speculative-decoding`. Verbatim from the body:

- "At temperature 0, enabling speculative decoding can change the generated sequence relative to
  plain decoding. This is already reported for ngram spec decode in #41758, and #52522 proposes
  batch-invariant support for speculative decoding — but scoped to the sampling layer".
- "The target model's verification pass computes rows with `M = k+1`, plain decode computes the
  same rows with `M = 1`, and **nothing in the current stack guarantees those two produce identical
  bits**."
- "The `VLLM_BATCH_INVARIANT` kernel work is the right neighbourhood, but its axis is batch
  composition across requests. Speculative decoding adds the `M=1 ↔ M=k+1` axis for the *same*
  logical row, which is the axis we found unguarded."
- "Should verify↔decode bitwise parity be an explicitly documented guarantee under a batch-invariant
  mode (with the cost that implies), or an explicit non-guarantee — so that users stop treating
  greedy-output changes under spec decode as a bug in their own configuration?"
- Magnitudes, each attributed: F16 GEMM M=5 vs 5x(M=1) "~92–114 of 20480 elements differ by 1–2
  ULP"; gated-RMSNorm under Inductor M=1 vs M=2 "1 FP16 element of 10240 differs, |Δ| = 7.63e-6";
  a numerically no-op custom op in one graph -> "downstream layer outputs differ at 1 ULP across
  ~2.3M elements"; "first divergent token index migrated 14 → 2 → 14 → 10 across successive true
  fixes"; "acceptance ~100% → 72% and decode ~110 → 89 tok/s"; end state "16/16 greedy-token parity
  at 1K and 4K with 81% acceptance".
- "Visible symptom ... Observed on SM70/V100 x4 (TP4), FP16 activations, a 125B hybrid
  linear-attention/MoE model with a native MTP head, full+piecewise CUDA graphs".

Corroborating issues (same channel, three further stacks):
- #41758 (cited by #54506 as "the symptom class ... Qwen3-0.6B, ngram, A100") — the existence limb
  on a third stack. Body not read (issue_read blocked); it is quoted by #54506.
- https://github.com/vllm-project/vllm/issues/53436 (2026-08-23, DeepSeek-V4-Flash, Blackwell
  SM120): instrumented the rejection sampler and found "at some steps the **target-logits SHA
  differs between the two runs**, for identical prefix + identical draft input"; acceptance rate
  "ranges 0.199 → 0.314 (**CV 14.2%**)" at fixed seed and correlates with throughput at
  "Pearson r = 0.98"; and critically for this candidate, in that regime the deviation did *not*
  reach the text: "final text is stable, throughput is not."
- https://github.com/vllm-project/vllm/issues/54785 (XPU, MTP k=4 + graph capture): "outputs cycle
  between 2-3 variants" at temperature 0, "byte-reproducible ... a deterministic function of
  request ordinal", "Any XPU user running MTP k=4 with graphs ... gets silently wrong greedy
  outputs. Throughput/stability testing does not catch it."
- https://github.com/vllm-project/vllm/issues/39273 (ngram on hybrid GDN): corrupted greedy output
  with spec on, and the expectation stated as the candidate's own premise: "Ngram speculative
  decoding should produce identical output to non-speculative decoding (with temperature=0, output
  should be deterministic and match)."

What this is and is not. It is NOT an answer to the candidate's estimand: nobody here reports a
distributional distance between served completion distributions, a permutation null, a confidence
interval, a spec-off/spec-off' composition-varied arm, or a quantization-step yardstick. The units
are bitwise tensor parity, greedy token-sequence parity counts, acceptance rate and throughput. It
IS the candidate's *question*, asked in the engine-maintainer vocabulary — "forward-pass batch
invariance across M for a fixed logical row", "verify↔decode bitwise parity" — including the
candidate's own treatment/nuisance decomposition (M-axis = treatment; batch composition across
requests = the nuisance the candidate's limb (ii) measures), and including the normative limb the
candidate's significance section rests on (should the guarantee be documented, or explicitly
disclaimed). The record's novelty sweep searched "vLLM batch invariance nondeterminism" and landed
on Thinking Machines write-ups; it never searched the M-axis / verify-parity vocabulary, which is
where the question actually lives.
