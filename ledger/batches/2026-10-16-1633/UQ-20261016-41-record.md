Question (canonical, Gate 0 as intaken):
For the elementary functions in deployed math libraries, how do the rate of last-bit disagreement between implementations and the distribution of error against the correctly-rounded result change when measured over the argument distribution that real scientific and machine-learning codes actually generate, rather than over the uniform-over-representable-domain weighting on which published worst-case error figures rest?

Question (canonical, Gate 1 reformulation — ONE reformulation used, for well-posedness only; both versions recorded):
Fix a precision (binary64 and binary32), round-to-nearest-even, a dated implementation set I = {glibc <v>, LLVM-libc <v>, one vendor CPU library (e.g. Intel SVML/VML high-accuracy mode), one GPU device library (e.g. CUDA libdevice), and its fast-math variant}, and a function list F = {exp, log, pow, sin, cos, tan, erf, exp2, rsqrt/1/sqrt, tanh}. For each f in F define, per observed argument x, the per-call predicates D(x) = "the results of the members of I at x are not all identical" and E(x) = "the result of a given member of I at x differs from the MPFR correctly-rounded value", with ulp error e(x) recorded. Then: what are (a) Pr[D(x)] and (b) the distribution of e(x), under (i) usage weighting — the empirical distribution of x over all calls to f recorded by interposition on a pre-specified, sampling-designed corpus of instrumented scientific and ML workloads — versus (ii) uniform weighting over the representable domain (exhaustive for binary32, stratified random for binary64); and by what factor do (i) and (ii) differ per function?
(The reformulation changes nothing substantive: it pins the implementation set, precision, rounding mode and function list, and replaces the vaguer "argument lies in a disagreement region" with a per-call predicate evaluated at each observed argument, which is what makes both limbs computable.)

Alternative formulations:
- Are the arguments at which glibc, LLVM libc, vendor CPU and GPU math libraries disagree reachable by production code at all, or do the documented worst-case ulp errors live in regions real programs never visit?
- What is the usage-weighted, as opposed to domain-weighted, accuracy of deployed libm implementations, measured by interposing on the math-function calls of a pre-specified corpus of instrumented workloads?

Motivating gap:
Deployed libraries ship "known maximum error" tables, and the periodic accuracy reports in the CORE-MATH / Zimmermann line document errors well above 0.5 ulp and disagreement between libraries and with correct rounding. Reading the glibc 2.42 edition of that report (OPENED, see below) confirms the measurement design directly: MPFR high-precision reference, exhaustive search for binary32 univariate functions (upper bounds), a recursive black-box worst-case search over the integer encoding of the input range with random samples per sub-range for binary64 and wider (lower bounds), worst cases cross-tested between libraries, explicitly no function-specific or application-specific test ranges, and no application-derived argument distribution anywhere. So every published figure is an extremum or a domain-uniform/adversarial sweep. The argument distribution real codes feed these functions is never the weighting, so the practical reachability of the documented error is unmeasured. The question sharpens in a regime where the argument range is narrow by construction: transformer kernels call exp on max-subtracted logits (a narrow negative band) and rsqrt in normalisation layers, and GPU fast-math variants carry errors orders of magnitude larger than CPU libm. The acting community is visibly choosing a test distribution with no application data in hand: the LLVM-libc GPU math project (OPENED) proposes "brute force testing" against OpenCL error bounds, with the gold standard debated between LLVM libm and MPFR, and says nothing about the arguments real GPU kernels produce.

Presuppositions:
1. Deployed libm implementations differ from correct rounding, and from each other, by more than 0.5 ulp on some arguments — ESTABLISHED, and now established from an opened source: glibc242.pdf reports per-(function, library, precision) largest known ulp errors against an MPFR reference, exhaustive and therefore tight for binary32 univariate.
2. The set of arguments a workload feeds a given function is a well-defined, measurable object. CONTESTED: it is input- and dataset-dependent. VPREC-libm (opened) is suggestive evidence in both directions — it records per-call-site operand interval boundaries and call counts across two SGP4 datasets, and notes that call-site indices "may not match" between datasets because execution paths differ. Within-workload-class stability is therefore an assumption the study must itself measure, which is why the stability check is part of the answer condition, not an add-on.
3. Math-function calls can be intercepted and recorded without changing the computation and at tolerable overhead. PARTLY ESTABLISHED for dynamically linked CPU calls: VPREC-libm (opened) interposes with LD_PRELOAD, states it "is not applicable to statically linked programs" (which must be relinked manually), and compiles with -fno-builtin so the compiler does not replace libm calls with hardware intrinsics — i.e. the known workaround is itself an admission that inlining defeats interposition. CONTESTED/partly unmeasurable for inlined intrinsics, vectorised libm entry points, -ffast-math builds and GPU device functions.
4. Correct rounding computed at higher precision (MPFR) is an adequate reference — ESTABLISHED for binary32/binary64; it is the reference the accuracy reports and LLVM-libc's own test infrastructure use.
5. Last-bit disagreement matters for some downstream quantity. CONTESTED and deliberately NOT required: "reachable but inconsequential" is an admissible answer, and the question is explicitly not about propagation.

What would count as an answer:
Per function in F, a pair of measured quantities with intervals: (a) the fraction of observed calls at which the implementation set disagrees (and, separately, at which a given implementation differs from the MPFR correctly-rounded value), and (b) the distribution of ulp error against the MPFR reference — each computed under (i) usage weighting from the pre-specified corpus and (ii) uniform weighting over the representable domain, with the ratio reported. The answer must include a stability check (the usage-weighted estimate reproduces across independent inputs to the same workload, and across workloads of the same class) and must state which call sites were unobservable by interposition and what share of calls that plausibly hides. Either direction settles it: usage-weighted rates orders of magnitude below the domain-uniform rate would show the published worst cases are effectively unreachable in production; comparable or higher rates would show real codes concentrate in the bad regions.

  REFERENCE/COMPARATOR: an internal binary128 (libquadmath) evaluation rounded to the target format via Verificarlo-VPREC, described as "a faithfully rounded result at target precision"; program-level correctness judged against the application's own test suite.

P2. P. Zimmermann (CORE-MATH line), accuracy report for glibc 2.42 and peer libraries — https://homepages.loria.fr/PZimmermann/papers/glibc242.pdf (opened).
  UNIT OF ANALYSIS: a (function, library, precision) triple.
  ENDPOINT: the largest known error e = |y - z| in ulps of z, y the library result and z the MPFR high-precision value; round-to-nearest-even only; reported to three decimals with the witnessing inputs tabulated.
  REFERENCE/COMPARATOR: MPFR at larger precision as the correctness oracle; other libraries as comparators, via cross-testing each library's worst cases on the others.
  ESTIMAND: the maximum of e over the representable domain — exhaustive and therefore an upper bound for binary32 univariate functions, a lower bound elsewhere (recursive splitting of the integer encoding of the input range, random samples per sub-range, exhaustive below a threshold of >=10^6 values, ~20 candidate intervals kept per level).   ENDPOINT: a sound worst-case absolute error bound tau = |f(x) - ftilde(xtilde)| (an analysis bound, not a measured error); running time in clock cycles as the objective.

Significance — consequence:
If usage-weighted disagreement and error rates come out orders of magnitude below the domain-uniform rate, then the "known maximum error" tables are a poor proxy for shipped risk, the case for spending speed on correct rounding in hot paths weakens, and the honest reporting unit for a library becomes a pair (worst case, usage-weighted rate) rather than a worst case alone. If they come out comparable or higher — which is a live possibility, since real codes concentrate mass in narrow bands (max-subtracted logits for exp, normalisation scales for rsqrt, small-argument regions for trigonometric functions) while the adversarial searches spend their budget on regions such as argument reduction near large powers of two that production code may rarely reach — then published worst cases understate practical exposure, and per-function prioritisation changes: the functions to fix first are not the ones with the largest known error but the ones whose bad regions coincide with where code lives. Either direction also re-prices GPU fast-math variants, where the error is orders of magnitude larger and the argument band is narrow by construction.

Significance — audience:
glibc maintainers (they publish the maximum-known-error table and have been absorbing correctly-rounded CORE-MATH implementations function by function, a per-function cost/benefit decision); LLVM-libc, whose GPU math effort is, on the record read above, choosing its testing distribution and its oracle right now with no application data; the CORE-MATH project itself, whose figures would gain a second axis; vendor libm teams who ship selectable accuracy modes (Intel VML high-accuracy vs low-accuracy, NVIDIA/AMD device libraries plus fast-math intrinsics) and currently justify the modes by domain-wide ulp bounds; GPU kernel authors choosing expf vs __expf or rsqrtf; and the HPC/ML cross-platform reproducibility community, for whom "do our codes even touch the arguments where these libraries differ" is the operative question behind run-to-run and platform-to-platform bitwise divergence.

Significance — fecundity:
Makes askable: (i) should a usage-weighted accuracy figure be a reported property of a math library, and over whose corpus; (ii) are measured argument distributions narrow and stable enough to justify generating domain-specialised correctly-rounded implementations (the Metalibm/RLIBM machinery already does restricted ranges, but takes the range as declared — P3 — so a measured range is a new input to a mature tool); (iii) which call sites are structurally unobservable, and what would an interposable boundary for GPU device functions cost; (iv) reachability as a prioritisation metric for correctness work generally, not only in libm; (v) the deliberately separated propagation question — does a reachable last-bit disagreement move any downstream quantity (loss, trajectory, eigenvalue) at all.

Significance — anchoring:
Touches the live standardisation push to make correctly-rounded elementary functions the default (IEEE 754 recommended operations, CORE-MATH's entry into glibc, RLIBM); the bitwise-reproducibility anomaly in HPC and in ML training/evaluation, where runs differ across platforms and libraries and the mechanism is usually asserted rather than localised to specific calls; and the long-running fast-math-safety argument, which is currently conducted with worst-case numbers on one side and anecdote on the other.

Reason for silence:
A disciplinary boundary reinforced by an evidentiary norm, plus an instrument gap on the newest half of the problem. Libm accuracy is owned by computer arithmetic, whose unit of proof is the extremum: hardest-to-round cases, proven ulp bounds, exhaustive sweeps for binary32, and black-box worst-case search above it (all visible in P2's method). A usage-weighted figure is corpus-dependent and so fails that discipline's publishability test — a referee's first question is "whose workloads?", and unlike a maximum it does not compose into a proof — whereas a maximum is auditable and portable. The people who hold the argument distributions are application and kernel developers, who have no reason to produce an accuracy report and whose own instruments (profilers, library interceptors) are aimed at time. The one community that did build exactly the needed instrument, precision tuning, pointed it at a different endpoint: VPREC-libm collects per-call-site argument intervals and call counts and then spends them as a search heuristic, so the profile is generated and discarded rather than reported as a finding. Finally, the regime where the question bites hardest — inlined GPU intrinsics and vectorised/fast-math paths — had no interposable boundary at all until GPU libm work became a first-class project, which is recent (the LLVM-libc GPU math profiling effort read above is 2025), so the sharpest version of the question is only now measurable.

Strongest remaining objection (pre-Gate 4):
The usage weighting has no sampling frame. "The argument distribution real scientific and ML codes generate" is not a population that can be sampled from, so the answer is a description of a hand-built corpus, and a sceptic can always reply that a different corpus would give a different number — which is also the reason the arithmetic community would not publish the figure. The candidate's stability check mitigates but cannot remove this: reproducing across inputs to the same workload shows within-class stability, not that the class is representative. Secondarily, the interposition blind spot may swallow the most interesting half of the measurement (inlined intrinsics, vectorised entry points, -ffast-math, GPU device functions), and the -fno-builtin workaround that makes CPU interposition work changes the code generated, so the observed call stream is not strictly the shipped one.
