Question (canonical — Gate 1 reformulation, the operative version):
For the N most-downloaded open-weight instruct repositories on the Hugging Face hub, (a) what fraction have at least one commit landing *after* the last commit that touches a weight shard which modifies a behaviour-determining non-weight artifact (`tokenizer*`, any `*template*`/`chat_template`, `generation_config.json`, `special_tokens_map.json`, `added_tokens.json`), where "behaviour-determining" is decided empirically by rendering a fixed prompt set under both revisions and diffing the resulting token-ID sequences and stop/EOS configuration rather than by diffing the files; and (b) with weight files byte-identical (SHA-verified), harness version, seeds, runtime and decoding parameters pinned, what is the paired score-delta distribution between the earliest and latest such revision on a fixed suite spanning format-sensitive tasks (instruction-following, tool-call, multiple-choice-with-stop) and format-robust tasks (perplexity, free-form), measured against a same-revision repeat-run noise floor obtained in the same study, and what fraction of those deltas exceed both that noise floor and the empirical distribution of improvement margins claimed as evidence in a sampled set of model-comparison papers?

Question (Gate 0 original, recorded as required):
For widely used open-weight instruct models, how often are the non-weight artifacts that determine behaviour — tokenizer files, chat template, generation config, special-token map — changed after the weights are frozen, and do those post-release changes alone, with weights and harness held fixed, shift benchmark scores by more than the margins papers routinely treat as evidence?

(The single permitted Gate 1 reformulation was spent on well-posedness only: it fixes the artifact file set, defines "weights frozen" as the last weight-shard commit, makes "behaviour-affecting" an empirical token-level test rather than a textual diff, requires the noise floor to be measured in-study rather than assumed, and operationalises the vague phrase "margins papers routinely treat as evidence" as a measured distribution of claimed margins. The question asked is unchanged.)

Alternative formulations:
- Does naming a model (rather than a model plus a revision hash) actually identify the system under test, or is a published comparison of "Model A vs Model B" underdetermined by config drift?
- With weights byte-identical, how large is the benchmark-score distribution induced by a model repository's own history of tokenizer/template/generation-config commits?

Motivating gap:
The settled practice being inverted is that open-weight releases are cited by name and the field treats the weights as the artifact while tokenizer files, chat template, generation config and special-token map are treated as metadata. That presupposes those files are inert and immutable. They are neither: they are mutable files in a git repository, routinely patched after release, and they decide prompt formatting, EOS/stop behaviour and default sampling. The hazard is currently visible in tooling rather than in the literature. Verified here by GitHub code search: `huggingface/lighteval` carries unit tests referencing a fixture repository named `lighteval/different-chat-templates-per-revision` (`tests/unit/models/vllm/test_vllm_model.py`, `tests/unit/models/test_transformers_model.py`; 24 code hits across forks/vendored copies), and that hub repository self-describes as "a dummy model repository to store tokenizers with different chat templates per revision / branch". So per-revision template divergence is a case an evaluation library writes regression tests against, while no study was found that measures how often it happens in the wild or what it does to scores. Widely discussed release-time EOS/stop-token and template fixes on major Llama and Mistral releases are recalled from commit histories and community reports and are NOT verified here (a search returned only community write-ups and talk abstracts, e.g. the AI Engineer 2024 talk "Fixing bugs in Gemma, Llama & Phi 3" at https://ai.engineer/talks/fixing-bugs-in-gemma-llama-phi-3, which was not opened).

Presuppositions:
1. Commit histories of hub model repositories are retrievable and permit distinguishing weight-freeze from later config-only commits. Largely true on the Hugging Face hub; assumes no force-push/squash and no re-upload of identical weight bytes. Mitigation: SHA-verify weight files rather than trusting commit order. FLAGGED, mitigable.
2. Config-only changes can be applied to fixed weights in isolation, so a score delta is attributable to the config and not to weights, harness, or runtime. Established in principle (the files are independently checkoutable); requires pinning harness and runtime versions explicitly.
3. Benchmark scores are reproducible to within a smaller margin than the drift effect under fixed weights, harness, seeds and decoding. CONTESTED — this ledger's own UQ-20261016-06 (Provisional) concerns residual nondeterminism in exactly this setting. Handled by measuring the noise floor in-study (same-revision repeats) instead of assuming it; if the floor swallows the drift, that is a legitimate "no" answer, not a failed study.
4. Published comparisons in fact cite model names without revision hashes often enough for the hazard to bite. Checkable; the reformulation makes it a measured quantity rather than an assertion. Unverified here.
5. A score shift caused by config drift is a defect of evidence rather than a legitimate improvement. CONTESTED and deliberately narrowed: a template fix usually makes the model *better used*, so the claim at stake is only that two papers citing the same name may have measured different systems — not that either measurement is wrong.

What would count as an answer:
A two-part study. (1) Census: for the N most-downloaded open-weight instruct repositories, enumerate post-weight-freeze commits touching the artifact set and classify each as behaviour-affecting or cosmetic by rendering a fixed prompt set under both revisions and diffing token-ID sequences, stop-token sets and generation defaults. Output: the fraction of repositories with at least one behaviour-affecting post-freeze change, with per-artifact breakdown and time-to-first-such-commit. (2) Experiment: with weights SHA-identical and harness/seeds/runtime/decoding pinned, evaluate earliest-vs-latest behaviour-affecting revision on the fixed suite, reporting the paired score-delta distribution and its tail against the same-revision repeat-run noise floor. Verdict: "yes, it matters" if a non-trivial share of repositories show deltas exceeding both the measured noise floor and the measured distribution of margins claimed as evidence in model-comparison papers, with the excess concentrated as predicted on format-sensitive tasks; "no" if deltas are indistinguishable from the noise floor across the suite, which would positively license bare-name citation.

Novelty — how this differs from each:
vs 1 (The Moving Target): same worry at the level of practice ("a score belongs to a specific artifact, not to a name"), different measured object. Its unit is a *new public generation* — weights change, so drift is confounded with genuine retraining, and its own exclusion list confirms it does not isolate non-weight files; it never mentions tokenizer files, chat templates, generation configs or special-token maps, has no census of commits, no byte-identical-weights condition, and no same-config repeat-run noise floor. Its three prompt templates are researcher-chosen variants, not the repository's own successive shipped templates. This candidate is the strictly-within-one-release case where weights are SHA-identical and the only thing that moved is a file the field classifies as metadata — which is what makes the result a claim about *artifact identity* rather than about model churn. The existence of this paper does, however, raise the risk that the candidate reads as its degenerate case, and is the main reason novelty is not High.
vs 2 (Ajibode et al.): covers the census half of the candidate, but on the other side of the weight boundary and with no behavioural measurement. It asks whether *weight* changes are reflected in version names; the candidate asks about commits that change *no* weights at all, and classifies them by rendered token sequences rather than by file diff or name. It reports no benchmark scores, so it cannot say whether anything it counted changes a number; it establishes that hub versioning is unreliable, which is a premise the candidate uses, not an answer to it.
vs 3 (FormatSpread): covers the sensitivity half, with a much larger effect size than the candidate needs — but the variation is synthetic, synchronous and researcher-generated, chosen to span a plausible format space. It carries no notion of revision, provenance or artifact immutability, and therefore cannot bound the *realised* drift: the open question is what the distribution looks like when the perturbation set is not "all plausible formats" but "the handful of edits the maintainers actually committed after release". A field can accept FormatSpread and still believe bare-name citation is safe, on the grounds that everyone uses the shipped template; the candidate tests exactly that belief. Note the composite risk: 2 + 3 together nearly imply the candidate's conclusion without measuring it.

Significance — consequence:
If yes (a non-trivial share of top repositories carry behaviour-affecting post-freeze config commits whose weights-fixed deltas exceed the measured noise floor and typical claimed margins), then a published comparison of "Model A vs Model B" by name is underdetermined: two papers can report different numbers for the same weights and both be correct, and a reported gap of the size the field routinely treats as evidence can be an artifact of which day the repository was cloned. That converts revision pinning from a tooling nicety into a reporting requirement, gives reviewers a concrete checklist item ("which revision?"), and makes leaderboard entries without a commit hash uninterpretable. It also predicts a directional bias worth naming: because post-release config commits are mostly fixes, later revisions should score higher, so scores attributed to a model name would creep upward over time with no change in the model — a confound in any longitudinal "progress" claim. If no (deltas sit inside the noise floor across the suite), the field gets something it currently only assumes: a measured licence for bare-name citation, plus a bound that makes the lighteval-style defensive machinery a correctness nicety rather than a validity requirement. Either answer is actionable, which is the mark of a real question rather than an advocacy piece.

Significance — audience:
(i) Evaluation-harness maintainers (lm-evaluation-harness, lighteval, HELM) — would move from defending against per-revision divergence in tests to recording and reporting the resolved commit SHA of every artifact alongside the score, and would know whether to warn when a user's local snapshot differs from the latest revision; lighteval's existing fixture shows this audience is already paying attention. (ii) Leaderboard operators — whether to re-run entries when a repository commits a template fix, and whether to version entries by revision. (iii) Venue reproducibility checklists and reviewers — a one-line requirement with a measured justification, which is what gets such requirements adopted. (iv) Model releasers — whether a post-release template or EOS fix is a silent patch or warrants a new revision tag and a note that prior numbers are stale. (v) Serving and inference teams — whether a cached tokenizer/template snapshot is an operational risk worth gating in CI. The audience's willingness to act is evidenced, not assumed: the defensive code and the pinning advice already exist; what is missing is the magnitude that tells them how hard to act.

Significance — fecundity:
Makes askable: what the right *unit of model identity* is for evaluation (name, revision, or rendered-prompt-plus-stop-config fingerprint) and whether a behaviour fingerprint can replace a hash; whether the behaviour-affecting/cosmetic classifier can be shipped as a release-time CI gate that tells a maintainer a config commit has changed behaviour; whether drift concentrates on format-sensitive task families as predicted, which would give a cheap triage rule for when pinning matters; whether the upward-fix bias measurably inflates year-over-year progress curves; and, jointly with UQ-20261016-06, how a total error budget for a benchmark number decomposes into nondeterminism, harness version, runtime and artifact revision.

Significance — anchoring:
Touches (i) UQ-20261016-06 in this ledger (residual nondeterminism under fixed seeds and harness), which supplies the noise floor this question must beat and is the reason presupposition 3 is flagged contested; (ii) the known harness-version confound in leaderboard scores (same weights, different implementation of a task), of which this is the artifact-side analogue; (iii) the semantic-versioning gap measured by Ajibode et al., extended across the weight/non-weight boundary; (iv) the closed-API silent-change problem (Gao et al., recalled unverified), as its public, logged, file-attributable complement — where the change can be *named*, not merely detected; (v) the prompt-format-sensitivity literature (FormatSpread and successors), to which it supplies the realised-perturbation distribution those papers leave unspecified.

Reason for silence:
A disciplinary boundary that runs exactly through the middle of the study, plus an incentive gap. The census half is empirical-software-engineering work: MSR-style hub mining, which has indeed mined Hugging Face repositories — but asks SE questions (naming, versioning, documentation, lifecycle, supply chain) and treats weight files as the payload, so it counts commits without ever running a benchmark. The experiment half is ML evaluation work, which studies prompt-format sensitivity energetically but generates its own perturbations, because a researcher-constructed format space is cheap, unlimited and publishable as a clean sensitivity result, whereas a repository's commit history yields a small, messy, non-i.i.d. perturbation set that requires provenance archaeology to assemble. Neither community owns the join, and the join is where the question lives. On top of that, the natural owners have an incentive to fix rather than publish: for a harness maintainer the finding's value is realised by adding a `revision=` argument and a regression test (which lighteval did), and for a model releaser by quietly patching the template; a measurement paper would instead impugn the comparability of numbers the whole community, authors included, has already published, so the cheapest path for everyone who can see the hazard is a closed bug rather than a result. A minor new-instrument component completes it: the census only became feasible once hub commit histories plus cheap re-evaluation made earliest-vs-latest sweeps across dozens of repositories affordable.
