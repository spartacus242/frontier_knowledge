Role: adversary. Gate 2 graded novelty Low (OpenMoE "Drop-towards-the-End" as near-duplicate of limb (a)). Treated as a prior finding, not inherited; all eight attacks run on their merits. Budget: 9/9 web searches used, 4/4 fetches used, plus one free GitHub code search. No search call was refused.

## Restatement (my own words)

Take public sparse-MoE checkpoints and run them at inference with an expert-capacity cap, so some tokens never reach their expert and ride the residual bypass instead. Fix beforehand (i) which of two rules decides who gets dropped — "whoever arrives late" (R1) or "whoever the router scored lowest" (R2) — and (ii) a set of groups the tokens belong to: language/script, document domain, how common the token is, where it sits in the sequence. Question (a): do dropped tokens come disproportionately from some groups, relative to the group mix of the input, under a pre-declared permutation test? Question (b): comparing each group's loss/accuracy against the same model run with the cap off on the same inputs, does a group's penalty rise with its drop rate, steeply enough versus run-to-run noise that someone choosing a capacity factor could predict which groups it will hurt? Crossed over at least 2 models, 3 capacity factors, both rules.

## Recommended verdict

Provisional at best: nothing Unresolved on attacks 1, 2 or 4, but attacks 3, 4, 6 and 8 are Partial and novelty on the canonical conjunction does not hold above Low (limb (a) is in OpenMoE). Promotion condition: re-pose as limb (b) only (paired per-stratum penalty vs capacity-free run, with dropped gate mass as a declared covariate alongside drop rate), and read Switch/ST-MoE for any printed per-stratum drop fraction.

Strongest killing point: every production or serving source opened says inference is run dropless (DeepSeek-V2: "do not drop any tokens for evaluation"; Huang et al.: capacity factor "usually set at high values during inference", dynamic gating so "token dropping will not happen"), so the regime the question audits exists mainly as the anchor's own proposal — and the one limb that is in-regime for training stacks, limb (a), is already descriptively answered by OpenMoE.
