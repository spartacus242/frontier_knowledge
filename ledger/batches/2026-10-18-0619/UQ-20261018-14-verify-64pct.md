Q1. Table at README lines 137-230 (header "World record history"). Numbers run 1..92 with no gaps; 94 rows because #21 appears three times (two are re-timings).
- First (#1): "45 minutes", llm.c baseline, 05/28/24.

- Previous (#91): 1.126 minutes (67.56 s), 08/06/26. So #92 is a 41% single-step drop from 1.126 to 0.665 (log(1.126/0.665)=0.527), larger than any other step in the series; its description lists many changes at once (sampled softmax, full FP8 MLP, 84.6M-row hashed n-gram table, ANVIL optimizer stack, depth reduction, mixed-width QK, CUDA graph). I did not open its log or PR #360, so the 0.665 figure is README-stated, not independently validated.
Q2. #21: "2.933 minutes", 01/26/25 (Reduced batch size, @leloykun). Re-timings of #21 (not new records): 2.997 min (02/01/25, "re-timing #21 with the updated rules"), 3.014 min (05/24/25, "re-timing #21 with latest torch"). Note records 1-21 are dated 05/28/24-01/26/25; "May 2025" is the date of the latest re-timing row, not of the records.
Q3. Seconds: first 2700; #21 175.98; current 39.9.
- Total = ln(2700/39.9) = ln(67.669) = 4.2146
- To #21 = ln(2700/175.98) = ln(15.343) = 2.7306
- Ratio = 2.7306/4.2146 = 64.8%
- Using 2.997 min re-timing: 2.7091/4.2146 = 64.3%; using 3.014: 2.7034/4.2146 = 64.1%.
- If current were taken as #91 (1.126 min): 2.7306/3.688 = 74.0%.
So "about 64%" holds only with #92 (0.665) as the endpoint and, strictly, with 64.1-64.8% depending on the #21 variant. It is not stable to the endpoint: before #92 it would be 74%.

Q6. Discontinuities, quoted from README:
- "After the 21st record, we made two changes to the timing." Grace steps replaced by untimed kernel warmup: "This results in an extra runtime of 850ms from the 10 extra timed steps." And "we banned the use of `torch._inductor.config.coordinate_descent_tuning`. This saves ~25min of untimed pre-run compilation, but results in an extra runtime of ~3s." Rule 3: "This rule was introduced after the 21st record." (Re-timing of #21 moved 2.933 -> 2.997, consistent with the ~0.06 min = ~3.8 s shift.) So the 1-21 segment is timed under different rules from 22+; the #21 original figure (2.933) is on old rules, while 22 (2.990) is on new rules. Using 2.997 would be like-for-like with #22+.
- Rule 4: "Run faster than the prior record when baselined on the same hardware." Hardware: "Official records are timed on 8 NVIDIA H100 GPUs from https://app.primeintellect.ai/." So record-to-record deltas are same-hardware comparisons; absolute times across the series are not one machine's clock.
- Target fixed at 3.28 for track 1 throughout (the 2.92 target is the separate Medium track). Rule: current record kept "roughly 0.001-0.002 loss below 3.28".
- Many records are software upgrades (PyTorch 2.5.0 #7, 2.9.0 dev #25, Torch 2.10 #66) and several are changes to batch/step budget, so log-additive accounting is an accounting convention, not a causal attribution.
