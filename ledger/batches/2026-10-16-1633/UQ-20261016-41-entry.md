Domain(s): STEM — numerical computing / scientific software (computer arithmetic, libm implementation); adjacent AI (kernel numerics, GPU fast-math)

Question (canonical): For the elementary functions in deployed math libraries, how do the rate of last-bit disagreement between implementations and the distribution of error against the correctly-rounded result change when measured over the argument distribution that real scientific and machine-learning codes actually generate, rather than over the uniform-over-representable-domain weighting on which published worst-case error figures rest?
(Gate 1 reformulation used, one only, recorded in full in batches/2026-10-16-1633/UQ-20261016-41-record.md: fixed precision, RNE, implementation set I = {glibc, LLVM-libc, a vendor CPU library, a GPU device library + its fast-math variant}, F = {exp, log, pow, sin, cos, tan, erf, exp2, rsqrt, tanh}; per observed argument x the predicates D(x) = "members of I disagree", E(x) = "member differs from the MPFR correctly-rounded value", with ulp error e(x); report Pr[D(x)] and the distribution of e(x) under (i) usage weighting from an instrumented corpus and (ii) uniform weighting over the representable domain, plus the per-function ratio.)

Alternative formulations:
- Are the arguments at which glibc, LLVM-libc, vendor CPU and GPU math libraries disagree reachable by production code at all, or do the documented worst-case ulp errors live in regions real programs never visit?
- What is the usage-weighted, as opposed to domain-weighted, accuracy of deployed libm implementations, measured by interposing on the math-function calls of a pre-specified corpus of instrumented workloads?

Motivating gap: Shipped libraries publish "known maximum error" tables, and the CORE-MATH/Zimmermann accuracy reports (glibc242.pdf, opened) obtain their figures by MPFR reference plus exhaustive binary32 sweeps and recursive black-box worst-case search over the integer encoding above it, with explicitly no function-specific or application-derived test ranges. Every published figure is therefore an extremum or a domain-uniform/adversarial sweep; the argument distribution real codes feed these functions is never the weighting. The regime where this bites is narrow by construction (transformer kernels call exp on max-subtracted logits, rsqrt in normalisation) and worst on GPU fast-math paths, and the LLVM-libc GPU math effort (discourse thread 84570, opened) is choosing its test distribution and oracle now with no application data.

Presuppositions: (1) deployed implementations differ from correct rounding and from each other by >0.5 ulp on some arguments — ESTABLISHED from opened sources (glibc242.pdf; RLIBM-32 Table 1); (2) the argument set a workload feeds a function is a well-defined measurable object — CONTESTED (VPREC-libm finds call-site indices "may not match" across two input sets of one application), so stability is part of the answer condition; (3) calls can be intercepted without changing the computation — PARTLY ESTABLISHED for dynamically linked CPU calls (VPREC-libm LD_PRELOAD, needs -fno-builtin; "not applicable to statically linked programs"; Glatard 2015 independently: "ltrace cannot be used on statically-linked tools"), CONTESTED for inlined intrinsics, vectorised entry points, -ffast-math and GPU device functions; (4) MPFR correct rounding is an adequate oracle — ESTABLISHED; (5) last-bit disagreement matters downstream — CONTESTED and deliberately NOT required ("reachable but inconsequential" is admissible).

What would count as an answer: per function, (a) the fraction of observed calls at which I disagrees and at which a given member differs from the MPFR value, and (b) the e(x) distribution — each under usage weighting and under uniform weighting, with the ratio, intervals, a stability check (reproduces across inputs to one workload and across workloads of a class), and a stated share of calls hidden from interposition. Both directions pre-stated and admissible: usage-weighted rates far below the domain-uniform rate would show the published worst cases are effectively unreachable; comparable or higher rates would show real codes concentrate in the bad regions.

P2. Chatelain et al., VPREC-libm, arXiv:2005.02732 (opened). UNIT: one libm call site in one binary. Significance — consequence: if usage-weighted rates fall far below the domain-uniform rate, the maximum-error tables are a poor proxy for shipped risk and the honest reporting unit becomes (worst case, usage-weighted rate); if comparable or higher, published worst cases understate exposure and per-function prioritisation changes to the functions whose bad regions coincide with where code lives. Either way it re-prices GPU fast-math variants, where the error is orders of magnitude larger and the argument band is narrow by construction. Discounted by adversary #3: for saturating functions the sign of the ratio appears fixed a priori by encoding-space bookkeeping, so the "factor" clause carries less information than the record claims.

Significance — audience: surviving audiences are GPU kernel authors choosing expf vs __expf, the LLVM-libc GPU math effort choosing its test distribution and oracle on the record now, vendor teams shipping selectable accuracy modes, and the HPC/ML cross-platform reproducibility community (Glatard's group acted on exactly this phenomenon). The CPU audience is deflating fast and on other grounds: LLVM-libc has proven worst-case bounds for all standard univariate double functions at speed parity (Microsoft C++ blog, 2026-09-16, opened), glibc is absorbing CORE-MATH function by function, and Intel announces "the first correctly rounded vector math library, to be available to users in mid-2026" (arXiv:2605.15547 abstract, opened).

Significance — fecundity: makes askable whether a usage-weighted accuracy figure should be a reported library property and over whose corpus; whether measured argument ranges are narrow and stable enough to drive domain-specialised correctly-rounded code generation (Metalibm/RLIBM take the range as declared); what an interposable boundary for GPU device functions would cost; reachability as a prioritisation metric for correctness work generally; and the deliberately separated propagation question.

Significance — anchoring: the standardisation push toward correctly-rounded elementary functions; bitwise irreproducibility in HPC and ML across platforms and libraries, where the mechanism is usually asserted rather than localised to specific calls; and the fast-math-safety argument, currently conducted with worst-case numbers on one side and anecdote on the other.

Reason for silence: a disciplinary boundary plus an incentive asymmetry, with an instrument gap on the newest half. Computer arithmetic's unit of proof is the extremum or an exhaustive count over the format — both auditable and portable, as a corpus-weighted figure is not. The people holding the argument distributions (application and kernel developers) have no reason to produce an accuracy report, and their instruments are aimed at time, bitwidth or memoization hit rate. The one community that built the needed instrument pointed it at a different endpoint and discarded the profile (P2). Adversary #3 adds a belief gap the record omits: the Muller/Lefèvre working heuristic that bits beyond the rounding position behave randomly makes usage weighting look irrelevant a priori. Weakened by RLIBM-32: the discipline does publish counts, so a frequency figure is publishable there and still nobody asked for the usage weighting.

Verification by the run session (one fresh-context checker over both priors and the usage-weighting question; 13 searches, 6 fetches, 2 refusals; full log in batches/2026-10-16-1633/UQ-20261016-41-verification.md). The verdict stands at Provisional. Arm (ii)'s prior art is confirmed, but the record over-reads what that prior art covers, and the single most important correction is that it cannot reach arm (i) at all.
(i) ARM (ii)'s PRIOR ART IS REAL. RLIBM-32 is a complete, format-uniform census of the binary32 domain: every one of the 2^32 input bit-patterns counts the same, each library is scored against the correctly-rounded oracle, and no usage weighting, application profile or empirical argument distribution appears anywhere in the paper. So the candidate's arm (ii) under uniform weighting is prior art for binary32, as the record says.
(ii) BUT TABLE 1 CANNOT GROUND ARM (i), AND THE RECORD IMPLIES IT CAN. Table 1 tabulates COUNTS OF INPUTS WITH WRONG RESULTS per library, each measured against the same oracle. Two libraries can both be wrong on an input and still agree with each other, so wrong-input counts cannot be differenced into a pairwise disagreement count. RLIBM-32 reports no implementation-versus-implementation comparison anywhere, and touches no GPU library and no fast-math variant. The candidate's first arm — how often deployed implementations disagree with EACH OTHER in the last bit — is untouched by it.
(iii) Four corrections to how the record cites RLIBM-32. Table 1's unit is "the number of inputs with wrong results", a count, not a rate; any percentage (0.70% for glibc float log10, say) is the reader's arithmetic, not the paper's. The words "exhaustive" and "exhaustively" never appear in its evaluation text and no sentence says "we evaluated all 2^32 inputs" — the exhaustiveness is carried by the caption's definitions, and the "2^32" sentence in section 4.1 is about something else. The word "sampled" DOES appear, but belongs to the polynomial-generation algorithm and weights by the density of representable values, i.e. by the format, never by program usage, so it must not be read as a usage weighting. And the library set is eight columns, not two: RLibm-32, glibc float, glibc double, Intel float, Intel double, CR-LIBM, MetaLibm float and MetaLibm double, over ten float functions, with posit32 in a separate Table 2.
(iv) Prior 2 confirmed on five of six absences and corrected on two readings. VPREC-libm never evaluates the deployed library's own error, never compares implementations against each other, uses call frequency only as a search-ordering heuristic ("we prioritize the call-site exploration by call frequency as a heuristic") and never as a weight, has no uniform-over-domain comparator, covers one application (SGP4), and has no GPU — all confirmed. Two corrections: its reference is a FAITHFULLY rounded result at precision p derived from a binary128 computation, not certified correct rounding, so it is a weaker guarantee than RLIBM-32's oracle and the two references are not interchangeable; and the application's test suite is not part of the oracle for the precision search — it validates the minimal SGP4 port, while the acceptance predicate is the user-specified correctness criteria.
(v) THE CENTRAL NEGATIVE IS INDEPENDENTLY REPRODUCED. Thirteen further searches found NO published measurement of elementary-function error, or of cross-implementation disagreement, weighted by an empirically observed argument distribution. The two priors bracket the question without answering it: RLIBM-32 measures error with no usage weighting, VPREC-libm uses real usage but does not measure error. One lead was left unopened when the fetch budget ran out — the LLVM libc GPU math profiling and conformance work — and it should be opened before this grade is relied on.
(vi) Half of one claim is marked unread rather than checked: whether the wider RLIBM project (beyond this paper) reports cross-implementation disagreement could not be established, because the repository read was refused and the companion papers were not opened.
