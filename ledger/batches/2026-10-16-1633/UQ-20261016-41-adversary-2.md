## Restatement (my words, before reading the generator's framing again)

Published accuracy numbers for shipped math libraries are maxima, found either by sweeping every binary32 bit pattern or by an adversarial hunt over the binary64 encoding. The candidate asks a different question about the same objects: when you instead record the arguments that real scientific and ML programs actually hand to exp/log/pow/sin/... and evaluate the libraries only there, how often do glibc, LLVM-libc, a vendor CPU library and a GPU device library give different last bits, and what does the ulp-error distribution against an MPFR correctly-rounded reference look like — compared with the same two quantities computed with arguments spread uniformly over the representable domain? The deliverable is a per-function ratio between the usage-weighted and domain-uniform rates, plus a stability check and a confession of which call sites interposition could not see. In short: *are the arguments where the libraries are wrong arguments that anyone's code ever reaches?*

## What the opened pages say

**RLIBM-32 (arXiv:2104.04043) — the record's Gate 2 query 8 is wrong.** The paper tabulates, per (library, function, format), the *number of inputs for which an existing deployed library produces an incorrectly rounded result*. Named cells include glibc float: ln 4.2E5, log10 3.0E7, exp 1.7E5, exp2 1.7E5, sinh 7.1E7, cosh 1.8E7; Intel float: ln 1060, log2 276, log10 1.5E5, exp 2.5E5, exp2 7.2E5, exp10 3.9E5, sinh 2.5E5, cosh 1.4E5, sinpi 3.4E5, cospi 3.8E5; CR-LIBM: ln 5, log10 1, sinh 2; MetaLibm float: exp 5.1E8, exp2 6.5E7, cosh 1.1E7; plus glibc/Intel *double* columns (ln 5, log10 1, exp2 2, sinh 2). Prose quoted verbatim from the fetch: "Multiple functions in glibc and MetaLibm's float library produce wrong results for several million inputs." And on its own sampling: "We sample inputs proportional to the number of representable values in a given input domain" — i.e. representable-value weighting, explicitly **not** application weighting; it "does not restrict input ranges based on profiling real programs".
  *My own arithmetic, flagged as mine:* taking the denominator as all 2^32 = 4,294,967,296 binary32 patterns, glibc sinhf's 7.1E7 is ~1.7% of the format, glibc logf's 4.2E5 is ~1.0e-4 (0.01%), MetaLibm expf's 5.1E8 is ~12%, Intel logf's 1060 is ~2.5e-7. Carried uncertainty: the table values as delivered to me are rounded to two significant figures, and **I did not verify the paper's denominator** — if the count is over a function's valid domain (e.g. ~2^31 for log) the fractions double. I also read the table through a summarising fetch rather than raw PDF text. So these are order-of-magnitude figures of my construction, not the paper's stated conclusions. The load-bearing point does not depend on the arithmetic: the counts themselves are published, per library and per function.

**Approximate softmax (arXiv:2501.13379) — the AI-accelerator vocabulary does not contain the candidate.** Its error evaluation uses "a test vector with 1000 random values within the softmax domain S=]-1,1[", assuming "a uniformly distributed discrete set within the domain", against Vitis HLS `hls::exp` as the baseline, reported as RMSE. Real-model runs (LeNet-5, MobileNet v2) report Top-1 accuracy only — no per-input numerical error. No comparison of glibc/Intel/CUDA. So this community both (a) declares its input range rather than measuring it, exactly like prior P3, and (b) answers the downstream question with a task metric rather than an ulp distribution.

**arXiv:2605.15547** — "Correctly Rounded Functions For Vector Applications: A Performance Study", Anderson, Cornea, Stepin, Panu (Intel). Abstract: SIMD correctly-rounded single-precision functions integrated into their CPU math library, some adapted to GPUs to exploit cross-platform bitwise reproducibility, plus proof-of-concept SIMD correctly-rounded double functions. No application-derived input distribution and no cross-library disagreement-frequency measurement in the abstract; full text NOT READ, so the record's second named residual risk is reduced, not eliminated.

## Single strongest killing point

The record's Gate 2 query 8 conclusion — "no published proportion-of-inputs figure surfaced ... the domain-uniform fraction appears not to be published either, which makes limb (ii) of the candidate partly new as well" — is false. RLIBM-32 (arXiv:2104.04043, opened) publishes per-(library, function, format) counts of inputs for which glibc, Intel libm, CR-LIBM and MetaLibm produce incorrectly rounded results, exhaustively for binary32. Arm (ii) of the candidate is therefore already in print for binary32 over much of F, the candidate's genuinely new content narrows to arm (i) and the ratio, and the Gate 2 record cannot be trusted as written on the limb it was most explicitly instructed to check.
