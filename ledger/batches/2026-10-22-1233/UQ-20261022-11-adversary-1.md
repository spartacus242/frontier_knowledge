## Attack 4 run first: the question's conditioning clauses, numbered, tested

1. CGPM Resolution 5 (2026) sets the maximum |UT1−UTC| at 3 600 s. — TRUE (source A, fragment as served). Caveat: the page as served does not print the 28th CGPM's meeting dates or the word "adopted"; I take the BIPM page at face value as the record did.
2. Continuous UTC becomes effective 20 May 2027. — TRUE (source A).
3. Each frame member "carries UTC−TAI or UT1−UTC", and "the largest |UT1−UTC| each can represent" is a defined quantity for each member. — FALSE for the UTC−TAI-carrying class, on an opened source. Source B defines `current-utc-offset` as "The offset between TAI and UTC". A field that carries TAI−UTC carries no UT1−UTC value at all, so it has no "largest |UT1−UTC| it can represent"; the question's threshold is placed on |UT1−UTC| (source A) and the field holds a different quantity. The record's own Gate 1 worked example instantiates the error: "IEEE 1588 / ietf-ptp current-utc-offset, int16, maximum 32 767 s ... so 3 600 s is representable with ~9.1 h of headroom" compares a UT1−UTC ceiling against a TAI−UTC field. Supporting inference, labelled as MINE: under continuous UTC with "long term continuity for UTC for several centuries" (source A), UTC is not stepped, so TAI−UTC stays at its 2027 value while |UT1−UTC| drifts toward 3 600 s over a century or more; nothing about the 3 600 s ceiling ever has to pass through a TAI−UTC field. (The resolution text as served does not state this about UTC−TAI; it is the meaning of "continuity", and source E's c.2000 framing — "By the time leap seconds add up to an hour" — describes the scenario the resolution rules out.) The question does NOT convert this into a measurand: V2's mechanism classifier (scalar / table / flag) does not classify by WHICH offset the scalar carries and reports no share of the frame carrying UTC−TAI versus UT1−UTC; so this is a presupposition, not a reported quantity.
4. 3 600 s is a threshold at which some frame members' representability can fail. — TRUE for the UT1−UTC-carrying class (source C: TF.460-6 Annex 2 codes DUT1 only to ±0.8 s; a 3 600 s DUT1 is not codable without a format change) — and that answer is already printed in the specification. Not applicable to the UTC−TAI class per clause 3.
5. The open-source members can be executed against boundary test vectors with a four-way failure alphabet. — UNVERIFIED (nothing opened bears on it; the leap-event test genre exists per S8 returns, not opened).
6. The public-artifact frame is enumerable with stated inclusion rules. — UNVERIFIED / plausible (the record's own four instances show members exist; enumerability of the whole not checked).

Clause 3 is one the V2 wording cannot survive without: "largest |UT1−UTC| each can represent" is the per-member estimand, and three of the record's four opened instances (ietf-ptp, linuxptp `currentUtcOffset`, NTP leap indicator, plus RTKLIB `utc_gps` GPS–UTC parameters / `leaps`) carry UTC−TAI or a leap flag, not UT1−UTC. Over that class the estimand is undefined and the 2027 threshold is inert. What is left is the UT1−UTC-carrying class (DUT1 radio codes per TF.460-6, IERS EOP products, the QZSS remark), which is small and for its headline member already answered by the specification itself (±0.8 s).
