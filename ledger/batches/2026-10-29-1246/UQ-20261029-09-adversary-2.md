## Restatement (my own words, before any attack)

Take a language model that is not a transformer — one whose whole memory of everything it has read
so far is a fixed block of numbers that gets overwritten token by token (Mamba-style SSMs, linear
attention, and hybrids of these with attention). Run such a model over a known stretch of text, stop,
and look only at that block of numbers. Question: **how much of the text can be reconstructed from
the block alone, counted in bits** — and, second, **how does that count compare with the raw storage
the block occupies** (number of slots × bits per slot), i.e. is the model packing its memory nearly
full or using a sliver of it, and is the sliver the same size across model families?

Two limbs: (A) an absolute bits-recovered curve against prefix length; (B) a utilization fraction,
A divided by the block's nominal bit count. Gate 1's "what would count as an answer" and the whole of
Gate 3 are written around (B).

### S1 — Parnichkun, Tumma, Thomas, Moro, An, Suzuki, Yamashita, Poli, Massaroli, "Quantifying Memory Utilization with Effective State-Size", arXiv:2504.19561v1, 28 Apr 2025
Authors taken from the paper's own front matter (F1). The PDF **names no venue**; aggregator pages
assert ICML 2025 — **not opened, so the venue is unverified**. The Liquid AI blog "How Effectively Does
a Model Use Its Memory" is a restatement by the same group (Poli, Massaroli) and is counted as **ONE
document with the paper**, not a second support.

- **REGIME:** population = synthetic MQAR / selective-copying / compression runs over GLA, WLA, LA and
  softmax attention; four 1B-parameter LMs (LA, WLA, GLA, SA) trained under identical conditions; and
  **pretrained open-weight Falcon Mamba 7B (Figure 7a)**. Unit of analysis = one model at one sequence
  index *i*, via the operator submatrix H_i = T_{i:,:i−1}. Operating condition = the materialized causal
  operator on given inputs; MQAR with kv up to 2^7. Instrument = SVD of H_i → tolerance-ESS (count of
  singular values above τ) and entropy-ESS (exponentiated normalized spectral entropy). Threshold = τ,
  no numeric value served. Category = **memory utilization in state dimensions (rank)**.
- **Numerator class, in the paper's own terms:** a **rank** — the number of significant singular values

  precision term at all**, and no readout of the state tensor — ESS is a minimal-realization argument
  on the operator, never a probe of `ssm_state`.
- **Denominator:** **TSS**, the theoretically realizable state-size = the state size of the model's
  recurrent formulation (for softmax attention, the sequence index *i*). **"State utilization" is

- **PUBLISHED IS NOT PERFORMED, applied.** The paper **defines and plots** the utilization fraction and

- **Overlap, both directions.** *What S1 misses that the candidate includes:* a bits numerator of any
  kind; the stored numeric precision, so quantization slack is invisible to it; any readout of the
  state tensor (and therefore the conv-state carrier entirely); prefixes of known entropy; and a scalar
  utilization value. *What S1 includes that the candidate excludes:* the operator/minimal-realization
  view; softmax attention as a comparator with TSS = i; ESS normalized by MQAR memory demand (ESS/kv);

### MY OWN ARITHMETIC (labelled as mine, from S3's integers)
Elementary step, **my own reasoning and not a source finding**: the state is a deterministic function
of the prefix, so the bits of the prefix recoverable from it cannot exceed the prefix's own entropy,
I(prefix; state) ≤ H(prefix) = L·log₂|V|. (Textbook information theory; I did not open a primary source
for it, and the search that would have grounded it was not run.)

- Carried elements per layer = `intermediate_size`×`state_size` + `intermediate_size`×`conv_kernel`
  = 8192×16 + 8192×4 = 131,072 + 32,768 = **163,840**.
- × 64 layers = **10,485,760 elements**; × 16 bits (bfloat16) = **167,772,160 bits ≈ 1.678 × 10⁸ bits**
  (≈ 20 MiB) of nominal carried capacity.
- Entropy of the candidate's **largest declared prefix**: L = 4096, log₂(65024) = 15.9886 →
  **65,489 bits ≈ 6.55 × 10⁴**.
- **Ceiling on the candidate's headline ratio at its own top rung: 65,489 / 167,772,160 = 3.90 × 10⁻⁴,
  i.e. 0.039%.** At the bottom rung (L = 16) the ceiling is 1.5 × 10⁻⁶.
- For the ratio to approach 1 the prefix would have to be L ≈ 1.678×10⁸ / 15.99 ≈ **1.05 × 10⁷ tokens**.
- **Robustness to S3's own inconsistency:** if `expand: 16` governed instead (d_inner = 65,536),
  nominal capacity is 1.342 × 10⁹ bits and the ceiling *falls* to 4.9 × 10⁻⁵. The conclusion holds
  either way, and strengthens under the alternative reading. The config's integers carry no stated
  uncertainty; the only uncertainty is which field governs, and both branches are given.
